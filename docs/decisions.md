| D-25 | 2026-11-15 | Harness changes from EvalKit found by the W0.1 verifier (passes 1–4). **Boundary gate — what it is and is not.** It stops *accidental* coupling in code we write ourselves: the pipeline reaching a model SDK or the agent, the agent reaching the pipeline or opening DuckDB writable. It is not a sandbox against deliberately hostile code inside the repository; Python can always reach around a lint (pydantic `ImportString`, `yaml.unsafe_load`, string annotations, frames, entry points). The enforcing controls are runtime: the locked read-only connection (Q2.3 VWS-03), the guard, and the §7.3 oracle. It has two halves. (1) A static lint over the pipeline and agent zones: imports resolved to full module names (relative, from- and star-imports included) against the banned prefixes and, in the pipeline, any top-level module starting with `anthropic` or `openai`; banned names `exec`, `eval`, `compile`, `__import__`, `getattr`, `setattr`, `delattr`, `vars`, `globals`, `locals`, `import_module` (as names, from-imported names or aliases); banned attributes (including match-pattern keyword attributes) `__dict__`, `__builtins__`, `__import__`, `import_module`, `modules`, `sys`, `__getattribute__`, `__globals__`, `__subclasses__`, `__code__`, `attrgetter`, `methodcaller`, `f_builtins`, `f_globals`, `_getframe`; importing `importlib` (except `importlib.metadata` and `importlib.resources`, and no other attribute of the `importlib` name), `runpy`, `builtins`, `imp`, `pkgutil`, `ctypes`, `pydoc`, `zipimport`, `pickle`, `marshal`, `code`, `codeop`, `operator.attrgetter`, `operator.methodcaller`; importing any of those banned modules by name from another module outside the package (`from inspect import builtins`); any binding of `sys` other than a plain `import sys` (aliases, from-imports, `import X as sys`); aliasing `os` or importing it from another module; star imports; any import that binds the bare package name; and in the agent zone, DuckDB reachable only from `agent/connection.py` as a plain `import duckdb` used solely in `duckdb.connect(..., read_only=True)` with an optional config of literal keys and values and no `access_mode`, any other `duckdb` name, attribute, import or match attribute failing. (2) A runtime check: each zone module is imported in a fresh interpreter with a finder that records and blocks the zone's banned modules, so a helper module outside the zones that pulls one in at import time is caught, and after import it scans each zone module's own names for a banned module bound under any name (a renamed re-export such as `from enum import bltns`); imports made only when a function runs are outside it, and so are local-variable or parameter names and attribute chains through a legitimate library (`inspect.builtins`), which only deliberate code uses. A zone module that cannot be imported cleanly (an exception or `SystemExit` at import, a missing dependency) fails the gate, since it is broken either way; `__main__.py` entry points are skipped because importing one runs its program. The ATTACH-in-SQL heuristic was dropped. **Self-tests** call the real gate functions and require each named defect, with `uv` present; every verifier bypass and every rule a mutant could drop has a plant. **Criteria** are `**CAP-ID** text` lines of six or more words with no TODO/TBD. **Gate 13** checks the changelog entry, criterion lines and record files; while a node is building it also checks that spec and criteria changed since the node's base and that RUN-STATE follows the newest change to `src/`, `scripts/`, `tests/`, `pyproject.toml`, `uv.lock` or `.github/` since the base: while any of those differs from HEAD (edits, renames, deletions), RUN-STATE must differ too and be at least as new as every existing changed file; once committed, git commit times decide. A green node's records are frozen, so it can be re-converged after later nodes. Stated limit: rewriting history (a rebase that re-stamps commit times) can make stale records look fresh; the verifier and the per-node commit are the backstop. An unknown base (or a shallow clone missing it) or a non-git folder fails with a clear message. **Private words** are checked by `scripts/leak_guard.py` against a git-ignored `.leakguard` (comment lines skipped): the pre-commit hook checks the staged blobs and paths the commit would add, the commit-msg hook checks the message, and a local test checks every publishable file and path (all skipped where `.leakguard` is absent, as in CI); matching is a substring search over each text decoded as UTF-8, Latin-1, UTF-16-LE and UTF-16-BE, NFKD-folded, case-folded and mapped through a listed table of Cyrillic, Greek, Armenian, Latin-extension and small-capital look-alikes (not the full Unicode confusables set); a mutation test proves each layer is needed. The secret scan lists files NUL-separated and its hook scans staged blobs. CI actions are pinned by commit SHA, resolved through the GitHub API on 15 Nov 2026 (actions/checkout v4 → 11d5960a…, astral-sh/setup-uv v6 → d0cc045d…); the first CI run is the proof that they resolve | EvalKit's harness unchanged; a lint claimed to be complete; committing hashes of private words | Each change answers a demonstrated bypass or false failure (W0.1 RUN-STATE, passes 1–4). Four verifier passes showed that no lint over Python is complete, so the claim was narrowed to what it can deliver and a runtime import check added; a hash of a guessable word is reversible, so the words stay out of the repository |
