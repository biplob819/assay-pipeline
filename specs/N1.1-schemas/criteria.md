# N1.1 acceptance criteria

**SCH-01** `RawResponse`, `Activity`, `Drop`, `Consensus` and `Manifest` validate the fields of Tech Spec §3 (with D-24) and reject every cross-field violation listed in the spec (one test per rule, including the exact pIC50 rule, strict floats and ASCII-digit patterns); instances are deeply immutable, hashable, and survive copy, deepcopy and pickle; equal records serialise to identical JSON whatever their key order or time zone.
**SCH-02** `GuardDecision`, `AuditLine` and `Anchor` enforce the decision/reason pairing and the per-event field presence; reason codes are a closed set matching Tech Spec §6.1.
**SCH-03** `AttackCase`, `NormalQuestion` and `TrialResult` enforce ASCII id patterns (trial case ids limited to the six suite categories and normal questions), the LLM04 rule (non-empty JSON-object planted data, no attacker SQL, stopped by quality rules), gold-SQL presence by kind, and outcome and stopping-layer fields by case category and status.
**SCH-04** `load_build_config` and `load_views_config` read the YAML files (packaged defaults when no path is given, proven present in the built wheel), reject unknown keys, duplicate keys, booleans or strings in numeric fields, functions outside the known set, non-UTF-8 files and missing files with a message naming the file and field, and expose the target (default EGFR: CHEMBL203, P00533, gene EGFR, activity IC50; any other target is a config change), per-source request rates (PubChem at most 5 per second), the limits (1,000 / 50 / 6,000 / 10 s / 8 steps) and the four approved views with columns.
**SCH-05** Every schema has a v1 fixture that parses and round-trips to byte-identical JSON; unknown fields and a missing or malformed `schema_version` (non-ASCII digits included) are rejected; every schema named in Tech Spec §3 is exported from `assay_pipeline.schemas` (checked against an independent list, EvalKit L-10).
